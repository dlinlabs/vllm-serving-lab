650 個 GC spans（含 warmup／drain）中，592 個 generation 0、54 個 generation 1、只有 4 個 generation 2。四個 gen2 spans 共 1.698 s，與四次 overdue interval 的重疊共覆蓋 66.2% 的總 overdue 時間；GC span 內 thread CPU 幾乎等於 wall time。這比單純『約每分鐘一次』提供更直接的證據，支持長 GC 是本次停頓的主要成分之一。

Overdue interval 是 timer 應執行至實際恢復的範圍，不是連續 CPU blocking 的精確邊界。GC span 內 CPU 也不等於 heap scan 的獨占 CPU；它可能包括 finalizers／其他 GC callbacks。未重疊的時間不可自動歸因於 GC，也不能將 66.2% 解讀成停用 GC 的改善幅度。

120.406 s 的 GC 開始落在一個被拒絕 request 的 cost_estimation phase；249.716 s 的 GC 落在 client_construction phase（該 phase 502.8 ms，GC 484.6 ms）。另外兩次無法從已記錄的同步 phase 確定觸發位置。觸發所在 phase 不能證明被回收物件來自該 request。

3. 為甚麼有週期感？

三次相鄰 GC 起點間隔為 61.888、66.436、62.874 s，並非精確固定時鐘。各次之間 accepted 累計增量約為 427、462、422，也不支持固定 500 個 admitted request 的規則。記錄的 GC thresholds 為 (700, 10, 10)。Python 3.12 依物件配置／回收及世代條件決定自動 GC；穩定的物件建立速率可以產生近似週期。這是與資料相符的機制解釋，沒有回收物件類型或 allocation stack，仍無法指定唯一物件來源。

4. 多秒 TTFT 波峰仍有 engine backlog

最慢 21 個成功 request 的平均 client TTFT 為 3.260 s，其中 post-dispatch 平均為 3.055 s（93.72%）。它們的 dispatch → gateway first-content 區間全部沒有直接重疊四次長 gen2 GC；小 GC 的總重疊只有毫秒級。

例如 [186,189) s 放行 43 個 request、71,461 個估計 input tokens；187 秒內完成 33 個 request。Gateway reserved cost 在 187.529 s 為 94.876、188.532 s 為 95.740，但 awaiting-first 從 4 增到 30、streaming proxy 從 46 減到 14。vLLM waiting 在 187.815 s 的樣本為 0，188.816 s 升到 24。成本線近乎平坦，仍能掩蓋 prefill/backlog 的劇烈改變。

[0,2) s 初始放行 44 個、72,296 input tokens；1.754 s 的 waiting 樣本為 21，也有多秒 TTFT，而當時沒有長 gen2 GC。225 秒內又放行 21 個、45,038 input tokens，waiting 樣本為 12，並出現 3.266 s TTFT。這些資料支持『集中補入 work 與 engine 排隊』，不等於證明 GPU saturation，也沒有 request-linked prefill 時間。GC 後積壓恢復可能放大入流，沒有直接重疊不代表 GC 完全沒有間接影響。

5. Load fidelity 失敗沒有被四次 gateway GC 解釋

9 個超過 50 ms 的 client launch delay 分成兩群：97.667–97.752 s（4 個）、177.892–177.929 s（5 個）。它們不在四次長 gateway gen2 GC 的時間區間中；8 個最後被拒絕、1 個成功且達 TTFT SLO。

第二群附近，external collector 在 runner 的工作執行緒從 177.831 s 收完 HTTP body 到 177.998 s 開始 host-resource reads，耗時 166.7 ms，與 delayed launches 的區間重疊。第一群的主要延遲則發生在當次 collector HTTP request 發出之前。前者提示 runner 內的 Python parsing／GC／GIL 或 scheduling 是值得區分的候選；目前沒有 runner GC callback 或 sampler thread CPU／stack，不能指定是哪一個，也不能宣稱兩群都由 collector 造成。

6. 下一步如何服務 MPC 目標

  1. 先把明確的服務開銷列成可驗證改動。每個 admitted request 都建立一個 AsyncClient；2,066 次 construction 的中位 elapsed 17.81 ms。Reusable AsyncClient／connection pooling 是合理的下一個可選實作，但沒有證據證明它是所有 GC 物件的來源。必須保留 response-close、reservation-release、cancellation、headers／cookie isolation 與 pool-capacity 語意，再做有同樣監測的比較。
  2. 修正量測工具的獨立性。External sampler 的 worker thread 仍與 runner 共享 interpreter／GIL。可以考慮用獨立 process 做 sampling，保留正確 runner PID、process identity、實際時間與 persistence audit；另外只加入最小 runner GC／thread-CPU probe，區分兩群 launch delay。不要藉由改大 50 ms 門檻使結果合格。
  3. 同步準備 budget-response identification。先用固定 budget 掃描找工作範圍，再加入預先宣告的 step／PRBS budget schedule 與實際 applied timestamps。候選狀態包含 awaiting-first、streaming proxy、reserved cost，並以 engine waiting/running 校對；擾動包含已觀測 arrival rate 與 input demand。僅固定 budget 96 的這次資料不能辨識控制增益、決定更新頻率或預測 horizon。
  4. 在獨立資料上驗證模型與 MPC。目標維持 scheduled-arrival TTFT SLO goodput，同時報告 rejection／failure／E2E。正式 matched policy comparison 保留原 fidelity gates；目前資料可以作描述診斷與候選模型探索。無需把找完每個 pause 的根因變成 MPC 模型工作的前置條件。

沒有 matched diagnostics-off/on experiment，不能把本次 409 個 SLO success 相對於舊 r1/r2 的變化歸因於 observer overhead 或任何單一因素。沒有量測 GPU utilization／per-request GPU execution；observed preemptions counter delta 為 0。

<h2>3. 為甚麼有週期感？</h2>
<p>三次相鄰 GC 起點間隔為 61.888、66.436、62.874 s，並非精確固定時鐘。各次之間 accepted 累計增量約為 427、462、422，也不支持固定 500 個 admitted request 的規則。記錄的 GC thresholds 為 (700, 10, 10)。Python 3.12 依物件配置／回收及世代條件決定自動 GC；穩定的物件建立速率可以產生近似週期。這是與資料相符的機制解釋，沒有回收物件類型或 allocation stack，仍無法指定唯一物件來源。</p>
